  Caso #1: A3 - Login con contrasena incorrecta
  --------------------------------------------------------------------
    Request:    POST /api/auth/login
    Esperado:   HTTP 401 Unauthorized
    Resultado:  HTTP 401 - CORRECTO

    Explicacion:
      Se envia password "wrongpass" para un usuario que existe en BD. BCrypt.matches() devuelve false. AuthService.autenticar() lanza ResponseStatusException(HttpStatus.UNAUTHORIZED, "Credenciales invalidas"). Este error es ESPERADO y demuestra que el endpoint rechaza credenciales invalidas.

    Assertion:
      pm.test("Status 401", () => pm.response.to.have.status(401))

  Caso #2: A4 - Registrar el mismo email dos veces
  --------------------------------------------------------------------
    Request:    POST /api/auth/register
    Esperado:   HTTP 409 Conflict
    Resultado:  HTTP 409 - CORRECTO

    Explicacion:
      El primer registro crea el usuario. El segundo intenta insertar el mismo email. La BD tiene constraint UNIQUE en la columna email, por lo que lanza DataIntegrityViolationException. AuthController.register() la captura y devuelve 409 Conflict. Esto asegura que no haya duplicados.

    Assertion:
      pm.test("Status 409 Conflict por email duplicado", ...)

  Caso #3: L6 - Obtener lista con ID inexistente
  --------------------------------------------------------------------
    Request:    GET /api/lists/99999
    Esperado:   HTTP 404 Not Found
    Resultado:  HTTP 404 - CORRECTO

    Explicacion:
      Se envia GET a /api/lists/99999. ShoppingListService.listById() busca en BD y no encuentra el registro. Lanza ResponseStatusException(HttpStatus.NOT_FOUND, "Shopping list not found with id: 99999"). El ID 99999 fue elegido especificamente por ser improbable que exista en BD.

    Assertion:
      pm.test("Status 404 Not Found", ...)

  Caso #4: L7 - Eliminar lista con ID inexistente
  --------------------------------------------------------------------
    Request:    DELETE /api/lists/99999
    Esperado:   HTTP 404 Not Found
    Resultado:  HTTP 404 - CORRECTO

    Explicacion:
      Mismo mecanismo que L6. DELETE a /api/lists/99999 busca la lista y al no encontrarla, lanza 404. Demuestra que tanto GET como DELETE manejan recursos inexistentes correctamente.

    Assertion:
      pm.test("Status 404 Not Found", ...)

  Caso #5: L8 - Crear lista sin token de autenticacion
  --------------------------------------------------------------------
    Request:    POST /api/lists
    Esperado:   HTTP 403 Forbidden
    Resultado:  HTTP 403 - CORRECTO

    Explicacion:
      Se envia POST /api/lists SIN el header Authorization: Bearer <token>. SecurityConfig tiene .requestMatchers("/api/lists/**").authenticated(), por lo que Spring Security intercepta la request antes de llegar al controller y devuelve 403 Forbidden. Nota: El pre-request script limpia el token de la coleccion.

    Assertion:
      pm.test("Status 401 o 403", ...)

  Caso #6: P6 - Agregar producto a lista inexistente
